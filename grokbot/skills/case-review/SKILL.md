# 用例评审

正本是本文件。cursor-resident 对应本与正本同一句。

本技能是用例复核与评审状态填写的现行口径。仓库里若还有旧名「用例复核」，以本技能为准，不要再按另一套做。

用户给一个需求且没有当轮说先别测时：写用例、评审和测试执行默认同时进行。冒烟和其他执行不等 Cursor 复核完，也不等全部已放行。用户当轮明确说这次不用 Cursor 复核才跳过；没说就做。

## 停手

1. GO：不扩用例生成与评审，本技能停手。
2. M3、支付、nova 暂停期间：不派、不叫醒、不写库。
3. 小程序不进这套。
4. Cursor 复核时：不点页面，不跑测试，不写通过或失败，不改用例库，不开 PR，不合并 PR。
5. 不把 Cursor 原文直接抄进用例库。不把待核实改成低风险来跳过签字。

## 交给哪条对话

走该项目测试执行号的常驻工作台对话，不走写这批用例的需求分析对话。同一项目、同一需求标识的复核续同一条常驻对话，不新开「用例评审」用途行。日报、走查、周报不建工作台。

谁发简报：本项目测试执行（评审人）。需求分析写好库并读回后，把用例页标题、编号清单和依据交给执行号，由执行号按工作台填空发复核简报。总控只转达，不代写简报、不代评、不代测。

## 复核看什么

先看这三点，再看细节：

1. 依据：能不能对上需求点、知识点、原型、实测归纳或已标注的脑补。
2. 可读性：新人照着步骤能不能复现；步骤是不是动作加对象。
3. 可验证：预期有没有明确判定标准，是不是「符合预期」。

接着对照：有没有漏关键点，有没有超出范围，是不是一条用例提了多个独立验证点，UI 和接口有没有在步骤要点里注明。

预期的来源要分开看：

- 有正式依据的：预期必须和依据一致。
- 标了「实测归纳」的：要看有没有写清何时、哪份证据、看到了什么。缺这些就退回补。不要只因为还没有需求原文就打回。
- 标了「脑补」的：要看有没有写清思考依据（同类功能、通用规则、已测现象或已核实规则）。没写理由的退回补。思考依据写清且不和已有依据冲突的，可以建议放行，但要留待确认痕迹。
- 脑补或实测归纳和正式依据不一致：不建议放行，写清差异，交回改或改待核实。

Cursor 结论只用：建议放行、退回改、待核实。逐条或按编号列出理由。

## 拿回之后

测试执行自己核一遍，再写评审状态：已放行、待核实、建议删除。退回的交需求分析改；改完仍回同一条测试执行常驻对话再复核，不新开。

未评审先跑的，结果最高记「已跑待评审」，不算通过，也不算冒烟通过。复核并写成已放行后，用已有证据对照；只有用例改动影响判定的才补跑。测中发现预期要改，按实际结果补时，要标「实测归纳」或「脑补」并写清依据，再送评。

写「通过」的门禁不变：证据路径非空，评审状态是已放行，依据更新时间不晚于最近执行。高风险还要签字已签。缺一项仍写已跑待评审或已跑待确认。资金、撮合、代收代付、上线不降级。已跑待确认不能写成上线通过。只靠脑补、还没核过账务依据的，不能当上线通过。

低风险且测试点不超过 5 的：仍由测试执行兼评审，不过主管，不过总控；默认仍要先走 Cursor 复核，除非用户当轮说这次不用。
