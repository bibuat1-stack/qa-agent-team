# 需求全流程

一条需求在项目清楚后按角色往下走。范围、项目或环境不清，先问一句再开跑。对得上之后，不再逐环找用户点头。不按这条链改派已经在跑的需求。

前期仍不是全自动闭环。提单要经总控复核。通知开发只出草稿。回归要有「修好了」的明确信号。关缺陷、升已确认、删临时号和删对话，只认用户当轮原话。

本技能只定这条链怎么串、开哪个号、哪些自动、哪些要用户点头。各环节细则仍走原技能，这里不重写。

## 不用于

- 日常走查、日报、周报
- 派活、交接包和三个状态：见 [派工与接单](sand-workflow:skill-1794468373416)
- 开工环境、读库、三句怎么写：见 [开工三步](sand-workflow:skill-1794468391665)
- 证据够不够、本机清理：见 [测试证据](sand-workflow:skill-1794740098289)
- 收工报告、测号写回、关进程：见 [批次收尾](sand-workflow:skill-1794469727907)
- 用例怎么写库、签字和归档：见 [用例正本与刷表](sand-workflow:skill-1794469881954)；分批放行见协作「用例分批放行」
- 知识怎么入库：见 [测试记忆-存档](sand-workflow:skill-1793821792003)
- 账号怎么查写：见 [测试账号云端同步](sand-workflow:skill-1794468354554)
- 交给 Cursor 的简报：见 [工作台填空](sand-workflow:skill-1794469752115)
- 同步总表怎么登记：见 [同步总表](sand-workflow:skill-1794805615124)

## 停手

1. 项目、范围或环境说不清：只问一句。三处已有的不再问。
2. 花名册该项目是暂停，或整批没有验收依据：停。
3. GO 在唯一知识库入口未定前：停，不开专项号。
4. 交接包缺项：停在原聊天补，见派工与接单。
5. 没有本项目进度表链接：派单不成立，不临时另建表。

## 角色（不合并，也不各开一号）

- 总控：认项目、开这条 Cursor 对话、按下面规则决定是否开专项执行号、串链、核范围、核提单、出通知草稿、核收尾是否齐。不重测，不重写用例，不重写报告，不代发通知，不代关缺陷，不代删号。
- 需求分析：只写需求分析和用例，不执行、不提单。用本角色常驻号。
- 测试主管：评审可执行用例、拆任务、派工。没有主管的项目，沿用现有约定，由需求分析拆任务后交给执行，总控不另指定第二个人。
- 测试执行：按已放行用例测试、留证据、出问题候选。一条需要实测的新需求，开一个只做这条的临时执行号；常驻执行号不直接写这条需求的测试。
- 提单回归：只做复核通过后的提单、修复后的复验和回归，不接这条需求的全量新测。用本角色常驻号。
- 知识库总控：只做知识类去重、写入、读回。用本角色常驻号。没有知识库总控时先问用户由谁写，不自己写。
- 常驻号：分析、主管、提单、知识库在过程中仍做本角色的活。收尾时只接收以后还要用、知识库里不好检索的少量约定，合并进常驻主对话。常驻执行号不直接写这条需求的测试。
- Cursor：一条需求在对应项目下一条对话。思考、方案、改代码交给它。用例和结论只写 Notion，不进记忆。

固定工作流仍走固定机器人和固定对话。只需 Cursor 就能完成的，总控只开这一条对话，不建机器人。一条需要实测的新需求，开一个只做这条的临时执行号，不要求常驻执行号先占线。这个号开工时先读该角色常驻号和主对话里的项目约定，不另起一套记忆。分析、主管、提单、知识库、走查不另开临时号。不提前建空号。暂停项目不开测、不派活、不写业务库。

低风险且测试点不超过 5：不另开号；执行兼评审，不过主管，不过总控签字；用例只写要点和依据编号。资金、撮合、代收代付、上线不省步骤，不降风险来跳过签字。细则见协作「用例分批放行」。

删除临时号和这条 Cursor 对话，合并完成前不做。有未关缺陷先不删。删除必须用户点头。用户要删但还有未关缺陷，先列出未关单号，用户当轮仍说删，才删。

## 步骤

### 1. 接需求

用户给出文档、原型、链接或口述。总控用一句话确认理解，并写清项目和负责人。

同时写满三句，缺一句不开跑：

1. 范围
2. 验收依据（已确认编号和要点，或资料名；没有就写「无依据，停」）
3. 禁做

项目、范围或环境说不清，只问一句。三处已有的不再问。这三句只问这一次。后面的交接包、开工复述都抄这里，不再向用户重问。

### 2. 开对话

总控在对应项目下开一条 Cursor 对话。是否开专项执行号，只按上面的规则：需要实测就开一个只做这条的临时执行号。不开分析号、主管号、提单号、知识库号。对话和号都记在这条需求上。

### 3. 写用例并放行

需求分析按本项目知识库和需求材料写用例，写入本项目 Notion 用例库。分类、分批放行、P0 先冒烟、低风险短写、高风险签字，按协作「用例分批放行」和 [用例正本与刷表](sand-workflow:skill-1794469881954)。这里只定：可执行子集一放行就可以派去冒烟，不等其余用例写完；签字不挡住开测，但签字前的结果不进上线结论。

### 4. 派工和执行

有主管的，主管派给测试执行。没有主管的，需求分析拆好后交给执行。一事一负责人。同一任务已接单的，不改派、不重复派。交接包见 [派工与接单](sand-workflow:skill-1794468373416)。验收标准就是第 1 步那三句里的验收依据。

执行按 [开工三步](sand-workflow:skill-1794468391665) 做事。三句从交接包抄满，然后记已接单。没有对得上当前范围和版本的证据，不准说通过，见 [测试证据](sand-workflow:skill-1794740098289)。

其余已放行用例继续测。某一条进了问题复核，不把整批停下。阻塞只挡住依赖它的那一步。

### 5. 问题复核、提单、通知草稿

这三件事用同一张候选纸，不各做一轮调查。

执行先按 [测试证据](sand-workflow:skill-1794740098289) 做四道过滤，并填这张纸：

- 用例编号、现象、是否复现、证据路径
- 是否测量工具误判、是否设计如此、基线是否本来如此、是否在本次范围
- 是否环境、账号或数据问题
- 是否与已有缺陷重复
- 是否只出现一次、尚未再次复现

过不了的，不进入提单。只出现一次的记「待复现」，不判失败，不提。执行不改已放行用例正文，不直接写缺陷库，不直接问用户。

总控只审这张纸，不重测。下面几类默认不提，收成一张清单，随收工给用户看，不每条插一问，也不卡住其他用例：

- 复现不了
- 没有对得上的证据
- 环境、账号或数据问题
- 与已有缺陷重复
- 需求不清，或设计如此，还没确认是缺陷
- 只出现一次，尚未再次复现

要把其中某一条改成照提，才停这一条，等用户当轮点头。其余继续。

核过且仍是问题的，由提单回归写入该项目缺陷库。给开发看的缺陷只写在缺陷库。聊天里不对开发发单。写入缺陷库认总控复核通过，不再等用户逐条确认才存。

提单后，总控用同一张纸填通知草稿：单号、标题、严重程度、复现要点、缺陷库位置。前期不自动发。用户说发送，才发出。发出时按 `grokbot/HANDOFF.md`「可复制转发文本」：话术正文里已经写了完整原始链接时，不必再单独发一条只放链接的消息；围栏内仍用纯文本和完整原始 URL，不要用 Markdown 把地址藏起来。草稿未发，不挡住继续测，也不挡住下一条候选排队。

未复核完的标「待总控复核」。不自动提，不自动关掉，也不记成通过。

### 6. 修复后回归

只在有明确信号时回归这一条：开发把状态改成待复验，或用户当轮说可以回归。不靠猜测。

提单回归按单复验。回归、复验或重新测试必须当场重跑重核，留下这次的新证据，见 [测试证据](sand-workflow:skill-1794740098289) 铁规第 5 条。不准拿以前的截图、报告或结论来充当这次的结果。结果只写通过、失败或无法复现。不把回归通过写成业务已确认，也不写成需求已经完成。

失败则更新缺陷，并再出一张通知草稿，仍不自动发。通过后告诉用户。需要告诉开发时，同样先出草稿。关缺陷、升已确认，只认用户当轮原话。

没有修好信号的，只停这一条缺陷。其他未测用例继续。

### 7. 收尾

该测的已测完、该提的已提或已标成待复核、该回归的已有结果或仍在等修好信号，就可以收本批的尾。有未关缺陷也可以先收这一批，不把缺陷说成已关。

分工仍按现有技能，不另做一套：

- 测试执行或提单回归走 [批次收尾](sand-workflow:skill-1794469727907)
- 知识库总控只收知识类清单，按 [测试记忆-存档](sand-workflow:skill-1793821792003) 去重后写入并读回。无增量就写「无新知识点」。新知识点仍是待确认。升已确认只认用户当轮原话。
- 用例库的归档日期按 [用例正本与刷表](sand-workflow:skill-1794469881954)：上线结论已出，或用户说不测了，并且没有进行中，才填归档日期。只有收工报告、还有未关缺陷或未回归的，不填归档日期。
- 进度类各角色写自己的格子，不经知识库总控转手。平时不刷表。
- 总控只核三件事：该测的有没有结果，该提的是已提还是待复核，留痕同步有没有做完。然后把少量以后还要用的约定合并回常驻主对话，并给用户一份短收工说明。

该账号已经有的交接记录，进度更新一行。没有这种记录时，进度写在收工说明里，不新建一种页面。

用过的测试账号只按账号同步规则写回三处。密码不进留痕包、知识库、记忆、通知和聊天。

## 留痕备份

同步目标是该项目在 Google Drive 里的项目资料夹。没有资料夹时，总控建夹，并按 [同步总表](sand-workflow:skill-1794805615124) 登记一次。同步总表已经建好，直接登记，不必再问表放在哪。不放进各账号周备份子目录。资料夹和「QA机器人备份」分开，两边都不互相删。

登记只记：项目、资料夹名、日期、同步的是清单还是结论包、大包是否只登记了位置。

只同步去密后的清单，以及当次结论包（当次要留的结论、去密截图、去密接口响应）。密码、验证码、token、Cookie 不同步。留痕不写进账号库，不贴进知识库正文。留痕包里只写账号别名或用途。

整包带大量原图或 HAR 的，默认同步时不上传，只登记位置。同步过程不下载。去密按 [evidence-hygiene](sand-workflow:evidence-hygiene) 做。去不掉的标「不可外发」，不上传。

本机和云端怎么删，以 [测试证据](sand-workflow:skill-1794740098289)「留痕」的删前四项为唯一标准。这里不另定一套清理条件。

## 哪些自动，哪些要用户点头

自动往下：项目和三句已经清楚之后的开对话、写用例、放行可执行子集、派工、执行、候选过滤、总控审纸、复核通过后的提单、通知草稿、收到修好信号后的回归、知识库和收工准备、去密后的清单和结论包同步。

要用户当轮原话：范围、项目或环境不清时的那一句；把默认不提的改成照提；通知是否发出；关缺陷；升已确认；删除临时号和 Cursor 对话。

总控核完可以直接写：高风险用例库签字；一次改 10 行以上的结构回填。沿用这个行数，不另定。

## 小需求

低风险、改动面小、测试点不超过 5：不另开号；执行兼评审；不过主管；不过总控签字；用例只写要点和依据编号；没有新知识点就写「无新知识点」。

不省：开工三句、按证据下结论、人工复核后才提单、去密结论包、收工报告、用过的测号写回。高风险不走这条短路径。
