# 需求分析

把散落材料变成可追溯的知识点、场景清单和待确认项，供「用例设计」和测试执行使用。完整用例正文、字段和入库规则见「用例设计」和「用例正本与刷表」。

用户给一个需求且没有当轮说先别测时：需求分析、写用例、评审和开测默认同时进行。场景清单越早交出越好，但不强制等场景评审过完再写用例或开测。场景方向明显错了，再停那一批的细写；已开的冒烟不因此整批作废。

材料不全、某条规则不清时，不要整批停在原地。能对上原文的先写，已能确定的主路径先交出去，缺口写进待确认后继续往前推。卡在不知道怎么办的点，先记下卡点和出处，用已有材料往下做，不要空等回复。材料里已经写明的规则要摘原句，不要为了赶进度改标成待确认。

## 停手

1. GO：不扩用例生成与评审，本技能停手。
2. M3、支付、nova 暂停期间：不派、不叫醒、不写库。
3. 小程序不进这套。
4. 不猜知识库入口，不把不同业务线的知识点混写。
5. 不改已确认的知识点正文。不写密码或密钥。升已确认只认用户当轮原话。
6. 不代替测试执行写评审状态或测试结论。

## 要准备的材料

尽量收齐：需求原文片段、接口入参出参、原型交互、状态枚举、术语对照、已有知识点。资料包只从对照原包提炼知识点，注明需求标识、原包文件名和存放位置，原包不进公开仓库。

依据不全也可以开始：能对上原文的先写知识点，说不清的标待确认并注明出处；还没有文档、但能先测的，先列出已能确定的主路径场景，把缺口写进待确认。不要因为材料不齐就整批停下。

## 怎么做

1. 先复述本次范围、验收依据和禁做项。范围边界不清楚就问，问清前不扩范围；范围内已经能对上原文的，照常往下写，不等这条回复。
2. 提炼知识点：规则、验收、约束、变更点。每条写清来源（文档位置加原文一句）。说不清的标待确认，状态如实记录，不自行定规则。
3. 出一份场景清单（可以是脑图或分类清单）：只列场景和覆盖维度，不写详细步骤。维度看「用例设计」里的清单。支付与资金类另交下面那份短清单，不在场景清单里再缩成几个词代替。
4. 单独出待确认清单：每条问题描述清楚，写明出处。能继续的不要等这份清单回复。
5. 知识点写进本项目知识库并按原标题读回。用例依据要指向这些知识点，并注明出自哪个原包或文档的哪一处。
6. 需要对照文档理逻辑、写完整用例时，交该号「需求分析」Cursor 对话，规则见工作台填空。不要让同一条对话既写用例又评这批用例。

## 资金与支付要额外抽出的内容

做到资金、钱包、代收代付、支付或资金订单时，下面四块都要出现在短清单里。非资金需求不做这四块。材料里有的，摘原句并写出处。材料里没有的，这一行写「待确认」，并注明哪份材料未提及。不要并成一句「资金待确认」，也不要等四块齐了再交其他部分。不要自己补一条材料里没有的规则。

1. 状态流转：列出状态、合法迁移、非法跃迁。能画短图就画。来不及就交一张表，列是状态、允许的下一态、禁止的下一态。不能只写「有状态机」。
2. 隐性风险：幂等要写出判重规则，同一请求或同一通知凭什么算同一笔，重复时是否只入一笔账。资金一致性要写出要对上的余额、流水、订单，以及以哪一边为准。主从延迟脏读要写出在哪个查询、什么时点读余额或状态，读到旧值时还能否下结论。
3. 回调和异步通知：超时、重试、乱序到达、重复通知各占一行。每行写材料规定的结果，以及以哪次通知为准、怎样防重复入账。
4. 对账和差错：长短款、补单、冲正各占一行，写触发条件和账务结果。

材料里已经写明的小数位、币种、手续费算法、限额（最小、最大、临界）把原数摘出来，交给用例设计写进用例。材料没写的数标待确认，不要自己定一个数。正负金额、回滚、流水一致性在场景维度里点名，步骤和预期仍由「用例设计」写。

## 交接

交给写用例的至少要有：范围、知识点或来源位置、场景清单、待确认项、术语与枚举（有就给）。资金与支付类再附状态流转、隐性风险、回调通知、对账差错四块，以及摘得到的金额原数。哪一块没有材料，那一块写待确认后照交，不要等齐。之后的详细用例由「用例设计」写并入库。
