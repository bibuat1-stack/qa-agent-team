# 需求分析

把散落材料变成可追溯的知识点、场景清单和待确认项，供「用例设计」和测试执行使用。完整用例正文、字段和入库规则见「用例设计」和「用例正本与刷表」。

用户给一个需求且没有当轮说先别测时：需求分析、写用例、评审和开测默认同时进行。场景清单越早交出越好，但不强制等场景评审过完再写用例或开测。场景方向明显错了，再停那一批的细写；已开的冒烟不因此整批作废。

## 停手

1. GO：不扩用例生成与评审，本技能停手。
2. M3、支付、nova 暂停期间：不派、不叫醒、不写库。
3. 小程序不进这套。
4. 不猜知识库入口，不把不同业务线的知识点混写。
5. 不改已确认的知识点正文。不写密码或密钥。升已确认只认用户当轮原话。
6. 不代替测试执行写评审状态或测试结论。

## 要准备的材料

尽量收齐：需求原文片段、接口入参出参、原型交互、状态枚举、术语对照、已有知识点。资料包只从对照原包提炼知识点，注明需求标识、原包文件名和存放位置，原包不进公开仓库。

依据不全也可以开始：能对上原文的先写知识点，说不清的标待确认并注明出处；还没有文档、但能先测的，先列出已能确定的主路径场景，把缺口写进待确认。不要因为材料不齐就整批停下。

## 怎么做

1. 先复述本次范围、验收依据和禁做项。不清楚就问，问清前不扩范围。
2. 提炼知识点：规则、验收、约束、变更点。每条写清来源（文档位置加原文一句）。说不清的标待确认，状态如实记录，不自行定规则。
3. 出一份场景清单（可以是脑图或分类清单）：只列场景和覆盖维度，不写详细步骤。维度看「用例设计」里的清单；支付与资金还要看幂等、金额精度、正负金额、对账、回滚、流水一致性、重复回调。
4. 单独出待确认清单：每条问题描述清楚，写明出处。能继续的不要等这份清单回复。
5. 知识点写进本项目知识库并按原标题读回。用例依据要指向这些知识点，并注明出自哪个原包或文档的哪一处。
6. 需要对照文档理逻辑、写完整用例时，交该号「需求分析」Cursor 对话，规则见工作台填空。不要让同一条对话既写用例又评这批用例。

## 交接

交给写用例的至少要有：范围、知识点或来源位置、场景清单、待确认项、术语与枚举（有就给）。之后的详细用例由「用例设计」写并入库。
