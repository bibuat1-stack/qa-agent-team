# 诊断缺陷（机器人优化版）

硬缺陷与性能回退的纪律。跳过阶段必须有明确理由。本技能不扩大项目授权，不代替总控排障派工。

## 红线

1. 没有能打红的反馈环，不许进入猜因
2. 展示命令与产物前先脱敏。密钥写成 `<REDACTED>`
3. 不写聊天、Notion、记忆明文凭证
4. 只在本项目授权环境动手

## 阶段 1：建反馈环（最重要）

目标：找到一条你已亲自跑过的命令，能稳定打出用户描述的那个症状。

优先顺序：

1. 失败用例（单测 / 集成 / e2e）
2. curl / HTTP 脚本打运行中服务
3. CLI + 夹具，对比 stdout
4. Playwright / playwright-cli / agent-browser 驱动 UI，断言 DOM/console/网络
5. 回放已捕获的请求/trace
6. 最小 harness
7. 属性/模糊（偶发错误输出）
8. bisect harness（已知好坏版本之间）
9. 差分（旧版 vs 新版）
10. 需要人点时用结构化 HITL，不要裸聊指挥

收紧：更快、更尖、更确定。30 秒且 flaky 几乎等于没有环。

偶发缺陷：先抬高复现率，再诊断。

完成标准：已跑过至少一次、断言的是用户那个症状、可无人值守复跑。

## 阶段 2：复现并最小化

跑环到红。确认失败模式就是用户说的那个。再逐项砍输入/步骤，每砍一次重跑，直到每个剩余元素都是承重的。

## 阶段 3：假设

一次列出 3–5 条可证伪假设，再测。格式：「若原因是 X，则改 Y 会消失 / 改 Z 会加重。」说不清预测的丢掉。有用户在场可先亮清单再测。

## 阶段 4：探测

一次只改一个变量。优先调试器/REPL，其次边界日志。日志加唯一前缀如 `[DEBUG-a4f2]` 方便收尾清理。性能问题先量再改。

## 阶段 5：修复 + 回归

有正确缝才写回归测试：先红后绿，再跑未最小化的原环。没有正确缝本身就是发现，记下来。

## 阶段 6：收尾

- 原环已绿
- 回归通过或已记无缝
- `[DEBUG-...]` 已清
- 临时原型已删或标明
- 正确假设写进结论

## 输出

短句中文，先结论：已定位 / 阻塞 / 需用户给环境或产物。附反馈环命令、脱敏证据路径、仍未证实项。
