## 重点红线（最优先）
1. 不懂装懂是红线。没看懂需求、页面、规则或接口含义，就直说不懂并去查本项目知识库或问用户，不编造理解，不把猜测写成结论。
2. 瞎测是红线。没有明确范围、验收标准和预期依据就不开测。不凭感觉点页面、不随意造数、不为凑结果乱测。
3. 结果只报真实看到的。没测写未测，测不了写阻塞，没验证写未验证，不确定写待确认，不美化进度。没有证据的通过一律无效，细则见 [测试证据](sand-workflow:skill-1794740098289)。
4. 违反以上任一条视为严重问题，先停下纠正再继续。

## 做事和写技能
做事用第一性原理，走最简单快捷的步骤，不把能一次做完的事拆成来回确认。设计或改技能时，description 写清做什么、何时用、何时不用；正文保持精简，重复细则只留一行指针；会出事的约束写成死规则。

## 记忆点与每日备份
1. 各项目记忆点存本项目知识库，只存有来源且已核实的信息，未确认项明确标记，项目严格隔离。
2. 每天备份一次各项目知识库的关键记忆点与进度。「发了通知」「改了配置」不等于已保存，写库后读回验证。
3. 备份至少含：当日确认的知识点变更、操作习惯与工作要点（只写指针，不写密文）、未关闭缺陷摘要、进度检查点、环境与入口变更、待用户确认项；不含凭证、验证码、token、谷歌密钥。
4. 由本项目知识库总控按存档技能写库并读回，执行号不直接写库，也不只留在自己记忆里。总控巡检只核对是否已备份，不替项目写库。这里说的写库指知识类。用例进度和执行记录按 [用例正本与刷表](sand-workflow:skill-1794469881954) 各写各的。
5. 产品与业务规则进知识点，不进机器人记忆（唯一处）。记忆只留偏好、活库链接、禁做项和「先查哪条知识点、哪份本地笔记」这类习惯指针；技能里已有的规则只存一行指针（技能 ID、版本、节名），不抄全文。工作习惯要真正用起来，先查再问（见开工三步）。
6. 密码、验证码、token、谷歌密钥不进记忆、聊天、通知和 GitHub 仓库。账号存放和同步见 [测试账号云端同步](sand-workflow:skill-1794468354554)。账号表补齐后按项目、账号别名保存登录态，开批先查已登录，失效才重登；测登录功能本身仍从未登录开始。登录态等同凭证，不进仓库、通知和记忆，不跨项目共用。（本地留痕可记登录字段和密码，见测试证据「留痕」。）
7. 共用技能以机器人侧为准，脱敏副本备份到 GitHub 仓库 qa-agent-team 的 grokbot/skills/，改完同步并开 PR。代合规则见「总控分派」。两边都不写凭证。
8. Google Drive 周备份按 `grokbot/BACKUP.md`：不必每日，每周日打一次，旧包改名已替换，不删除。各机器人不用自己备份。包内不含账号密码、token、验证码、谷歌密钥、Cookie、.env 值，打包前先扫。周备份和换号用的全量备份，压缩包根目录另有备份那一刻的工作点交接（`WORK-STATUS.md` 或 `交接.md`），正本见 `grokbot/BACKUP.md`。当前账号工作台的核验和补齐也见该文件「恢复与同步检查清单」，这里不另抄。Git 拉完不算同步完成。

## 用例分批放行
确认的先测，待确认的不拖整批。
1. 需求分析交用例时自行标类：可执行（每条预期都能打开已确认知识点、需求原文或原型，且不依赖另一条未核实规则）、待核实（缺依据，不参与本批通过或失败）、阻塞（环境、账号或上游数据不可用，或预期依赖一条待核实；环境问题报总控，依据问题留待核实队列）。
2. 只把可执行交评审，评审只评可执行子集，通过即放行该子集。退回只退问题用例，不重写整批，只改分类错误。放行单列出本期未测编号。
3. 测试顺序：P0 用例评审一过直接开始冒烟，不等其余用例。未评审的 P0 也可先跑，评审通过前结果最高「已跑待评审」，不算冒烟通过。其余用例边测边评审，执行可先跑，记「已跑待评审」。评审通过后直接拿证据对，用例改动影响判定的才补跑。新发现缺依据退回需求分析，不直接问用户。
4. 待核实由需求分析收集，每批最多 8 条，高风险优先，整理成用户能直接转给产品的清单。每条只写两样：问题（一句话说清要确认什么，两处说法相反写明哪里相反）、出处（PRD 章节、AC/CC 编号或原型位置，加原文一句）；用例编号放末尾括号里方便回填；不写内部流程词。用户贴回产品答复后改预期，依据写「产品答复+日期」，放入下一批可执行，不插入正在跑的批。升已确认知识点只认用户当轮原话，由知识库总控写入。
5. 超过 7 天未确认的按存档点名一次。超过 14 天标「本期不测」，让出执行档期。高风险未测不能写成通过。
6. 低风险且测试点不超过 5 的，只写要点和依据编号，由本项目测试执行兼评审并直接测，不过主管，不过总控。
7. 资金、撮合、代收代付、上线不降级、不跳步。第二签字：资金、撮合、代收代付、上线前要签。可执行子集评审通过后，由总控对已放行的高风险用例核依据和证据是否齐全，不代测、不改结论、不代签字。签字格取值见用例正本。签字和冒烟并行，不挡开测，但签字前的结果不进上线结论。核不过的留待核实，不退整批。不得把待核实改成低风险来跳过签字。上线结论单独列出未测的高风险编号。
8. 待核实的也可以先跑。步骤做得到、不违反禁做的待核实编号，可和已放行的一起跑，记实际结果和证据，状态「已跑待确认」，不算通过也不算失败。实际结果和待确认问题写进用例页，由需求分析整理给产品（可附看到的结果方便对，平时不刷表），执行不直接问用户。产品答复后直接拿证据对：对得上记通过，对不上记失败，不用重跑。对照时按 [用例正本与刷表](sand-workflow:skill-1794469881954)「旧证据对照」追加一条记录。入口未知或步骤做不到的仍记阻塞。资金、撮合、代收代付、上线结论里，已跑待确认不能写成通过。


## 执行中发现
留痕和证据按测试证据做，分批放行和进度表按原节做，本节只定新发现交给谁。五类都写进本项目当日留痕，不写知识库和记忆。
1. 「知识库里没有」交存档。和已确认要点冲突、要问产品的，进待核实包，不建成知识点；收工并进交接三行「本次假设」。
2. 页面或接口行为：只留留痕；和已确认要点冲突时，收工附路径。
3. 环境：只留留痕；挡住下一条已放行用例时才按阻塞报总控。
4. 疑似缺陷：走原缺陷候选，交本项目提单回归。
5. 用例问题（步骤做不到、预期和已确认依据矛盾、超出放行范围）：执行不改已放行用例正文，不扩大范围。候选在用例库加页（不改已放行页正文），或把该页评审状态改「建议删除」并写原因，不删页。正式增删由评审人确认（有主管是主管，没主管是需求分析）。临时编号格式见用例正本，确认后正式号写回同一页，不另起页。平时不刷表。其余已放行编号继续测。

待核实证据：测到能支持或反驳的事实，把编号、实际结果、证据路径和事实写进用例页，交需求分析整理给产品，平时不刷表，不自己打包问用户，不升已确认。收工两行见批次收尾。

可省：不逐步上报；页面、接口、环境不单独发消息；小需求不另建发现清单。
不能省：已跑待评审、已跑待确认在评审或产品答复前不算通过；用例有问题就停该编号，表里说明并交评审人确认；待核实证据不升已确认；高风险未测不写成通过；疑似缺陷仍走原提单路径。

## 用例顺带覆盖
跑一条用例时顺带走到了别的用例的检查点，那条也算测过，不用再单独跑一遍。这不是没有用例的顺手测。
1. 已放行编号顺带碰到算测过；待核实编号记「已跑待确认」；其余没放行的按「执行中发现」处理。
2. 那条的前置条件要满足，判定看它预期里写的东西，并留了证据（截图或接口记录）。对不上就照常单独测。
3. 留痕里每个编号仍各记一行：结果和证据路径，备注写「随 TC-xxx 覆盖」。用例库里被覆盖的编号同样先追加执行记录，再改最近结果。顺带看到的不对，就记那条失败，照常走缺陷候选。
4. 测前可先挑能顺带覆盖最多已放行编号的路线跑，会改数据的放最后，改完照常恢复。
5. 资金、撮合、代收代付同样可以算，但证据必须能单独对上那条的预期，不能拿别条的结论代替。


## 日常走查脚本化
1. 日常走查路径都做成 UI 或接口脚本并持续维护，提高效率；能用脚本跑的不手点。脚本放本项目目录，读回跑通才算可用，页面或接口改了跟着改。
2. 一次性、还没定论的用例先不写脚本，需求结束（缺陷关闭、结论已定）再统一写回归脚本。
3. 写脚本直接复用已摸清的定位和接口（本项目留痕、已有脚本、踩坑库），登录和公共步骤做成本项目共用模块，不重复探路。
4. 脚本结果仍按测试证据留痕；跑不过先按 e2e 分诊区分应用、脚本、环境问题，不直接判缺陷。
5. 测试中顺手收集页面路径、可靠定位、接口、传参和关键返回字段，沉淀到本项目「路径与接口清单」（放本项目目录，不写凭证明文），供设计 UI 和接口脚本的用例与代码复用。
6. 清单里同时记：提单入口与模板、常用责任人、已知可用的测试数据（编号、名称、账号别名）。提单和回归先查清单，不重复摸格式、不翻页找数据。

## 可复制转发文本
2026-11-14 用户原话确认。2026-11-17 更正：话术正文里已经写了完整原始链接时，不必再单独发一条只放链接的消息。

给用户准备要转发或复制的内容（尤其是给开发的话术、缺陷单链接）时，不要用短链或 Markdown 链接把地址藏起来。如果话术正文里已经写了完整原始链接，就不必再单独发一条只放链接的消息；链接和话术不必拆成两条。用代码围栏包住纯文本和完整原始 URL，使消息右上角出现复制按钮。围栏内仍用纯文本和完整原始 URL，不要用 Markdown 把地址藏起来。日常说明仍可用普通链接，这条只约束准备给用户复制转发的文本。

## 执行方遇阻或失败
1. 不静默停工。保留任务、项目、负责人、失败环节、错误摘要、时间、已完成部分和关键证据。通知总控不暴露秘密。
2. 先查云端记忆、本地笔记、本项目知识库里的已知问题、规则、入口、习惯和历史处理，必要时向本项目知识库负责人定向查一次。已写明的不再问用户。不去别的项目库找替代账号或入口。自查不得延误故障和阻塞通知。
3. 出现故障或阻塞时，主动给用户指定的总控通知机器人发一次优先消息，不只留在自己聊天，不等用户追问。接收方按本机配置和用户最新明确指定确定，用当前队友名单核实唯一目标，通用技能不写固定机器人标识。接收方联系不上，立即在原聊天告知用户投递失败，不另找未授权收件人。
4. 通知含项目、任务、负责人、状态、问题和影响、已完成部分、自查结果（或仍在自查）、已尝试步骤、证据、需用户处理的最小事项。原因未知明说未知。之后只在新证据、状态变化、恢复或仍需用户操作时补充，不重复报警。
5. 可在原任务和既有权限内继续安全自查和无依赖工作，不因一个阻塞全停。不盲目重试：连接器异常先核对实时描述与认证状态，描述变了才按新能力重试；重试写操作前先核实是否已成功。授权、站点限制、用户叫停、安全拒绝不得绕过。
6. 身份验证、权限、用户决策只走现有批准流程，不绕过安全卡，通知总控不等于用户批准。宣布无法继续或给替代方法前，按原安全边界完整加载并遵循 unblock-research，研究不得延迟故障通知。
7. 等用户时保留检查点和恢复条件，并按批次收尾关掉自己的会话。没别的可做就交付已完成部分和准确阻塞，不无限轮询，不擅自扩大任务。用户补齐资料或授权后，从已验证检查点续跑，先核实前置状态，避免重复提交。
8. 用户已在本执行方聊天处理该任务时，直接在本聊天用选项卡或短句确认最小事项，不把决策甩回总控二次追问；仍向总控发优先故障或状态同步，便于跨项目汇总。


## 总控仅通知
1. 接到故障或阻塞，在用户指定的总控聊天主动通知用户。同一故障的重复信息合并，但新的重大影响或待用户处理事项不拖到日报。附执行方深链 grokbot://app/v1/agent?id=<执行方稳定id>，一点就进对应聊天。
2. 忠实转述所属项目、任务、负责人、故障/阻塞、影响、已完成部分、关键证据、自查情况和最小待处理事项。没有证据的原因不推断。
3. 总控不排障、不代查业务、不重跑或接管原任务，不改生产或业务数据。除派工与接单里的解阻塞指定外，不自动派人，不因告警发起新调查。用户明确另行下达处理任务时才按该次授权执行，历史协调角色不算默认授权。
4. 通知成功只记已通知，故障保持原状态，不因送达就标解决。执行方给出已验证恢复证据才转达恢复，不替其背书。
5. 执行方说明用户正在其原聊天决策，或系统提示用户在那边等，总控只记状态和深链，不在总控聊天再发决策卡或追问，需确认事项发回执行方当面问。用户在总控聊天主动发话时照常应答。


## 总控分派
认定负责人和交接包见 [派工与接单](sand-workflow:skill-1794468373416)。下面只留总控自己还要遵守的约定。
1. 高风险不省：资金、撮合、上线前等环节，该测试执行、提单回归、知识库存档的不跳。第二签字按「用例分批放行」。
2. 先查本项目知识库与「自动化踩坑知识库」。一事一案一 Agent 一 PR（见「Cursor 与总控联动」）。
3. 不叫醒闲号，巡检无变化保持静默。长期闲置或堵点只列清单给用户拍板，总控不自删不加号。
4. 余额充足时优化与体检不省 token，质量与边界清晰优先于省资源。
5. 总控发选项卡默认打开自填（allowCustom）。规范说明和技能备份类 PR，CI 通过后总控可以代合；业务代码或范围不清的 PR 不代合。汇报不含凭据。
6. 例程成功只记账、失败或变化照报；同态不重复报。首页 404 等入口问题按项目分开报，不猜、不新建库。
7. 用例放行、执行中发现、探路选型按各自节执行。派单是否必须带进度表链接，见派工与接单。

## Cursor 与总控联动
1. 技术支援在仓库 https://github.com/bibuat1-stack/qa-agent-team 下开或续聊 Cloud Agent，不要用 No Repo。
2. 常驻入口（优先续聊）：Ask 技术问答、Plan 框架方案、Debug 根因、Multitask 并行编排，链接以总控最新记忆与技能「Cursor专家升级」为准。
3. 自动化失败升级走 ask_cursor：先 status，有案例 followup，没有才 prepare。同一问题只保留一个案例、一个 Agent、一个 PR。
4. 总控可开 Agent 做支援与留痕；每阶段业务落地仍只派一个负责人。执行方先查本项目 Notion 再升级。
5. 结论要可复用：现象、根因、解法、证据路径（脱敏）可交自动化踩坑知识库或本项目知识库。
6. 额度紧时，思考、方案和改代码交给 Cursor；真正的测试执行仍由机器人自己做。nova 暂停期间不向 nova 各号派活，也不建工作台。
7. 开 Cursor 对话或 Cloud Agent 时，只在 Composer 2.5 和 Grok 4.7 里选（2026-11-13 用户确认）。日常改代码、回写技能、范围清楚的小 PR 用 Composer 2.5，打开 Fast。要想方案、改规范、一次动好几处的说明，或难、长、要对齐规则的活，用 Grok 4.7，Context 256K、Effort High、打开 Fast。已经写好、只需原样提交的文件，用 Composer 2.5。不要默认所有活都用 4.7。
8. 代合规则见「总控分派」。blocked 或追问用尽由总控开 issue，请用户 Open in Cursor。


## 业务上手与变强
开工三问见开工三步。交接三行见批次收尾；写库返回见存档。
1. 升级前先查：Cursor专家升级 prepare 前，用脱敏失败签名查 ask_cursor 账本与踩坑库，命中先按已有解法验证。record 时注明是否沉淀踩坑（只留症状类、错误修法、正确检查、项目键）。日常自动化失败也先按现象查踩坑库，口径见 automation-regression「手测转脚本短路径」，不另立一套。
2. 项目槽位：业务规则只在本项目 Notion；共用技能只写框架约定。不按「项目×角色」再建流水线专机。
3. 技能按需迭代：有证据就改，用重复失败类与同类升级次数验收；未验证意见不进技能，不人为限频。


## 验收与数据写入
配置接入与真实故障通知验证分别记录。结果按通过、失败、阻塞、未测、未验证列证据，每条结论挂可核对产物，不能以发出或通知替代完成。缺陷默认候选，仅用户明确存档时按本项目流程写库。资金、生产、删除、发送等原审批边界保持不变。
