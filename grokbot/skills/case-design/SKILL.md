# 用例设计

用户给一个需求且没有当轮说先别测时：写用例、用例评审、测试执行默认同时进行。不必等场景全评完、用例全写完或评审全过完再开测。测的过程中可以按实际结果补全或修正用例。写库字段、状态词和刷表时机仍以「用例正本与刷表」为准，本技能只管怎么设计和怎么写正文。

覆盖必须全面：下面的场景维度（含资金与支付项）都要扫到，不为赶进度删维度。某一维适用时，至少落一条用例；写不清的标待确认或按下面规则标脑补，不能只在覆盖自查里点一个名。整维不适用要写明原因。材料里已经写明的规则，不要改标成待确认。某条写不清时，先完成已能写的用例并入库开测，不要整批卡死。

## 停手

1. GO：不扩用例生成与评审，本技能停手。
2. M3、支付、nova 暂停期间：不派、不叫醒、不写库。
3. 小程序不进这套。
4. 没有范围、验收标准或任何可依据来源（需求、原型、接口、已有知识点、可对照的实测）时：先问清楚再写，不硬编。
5. 不要把多个独立验证点合并到一条用例。不要写「符合预期」这类不能判定的预期。
6. 升已确认、关缺陷只认用户当轮原话。不改已放行用例正文；测中发现要改正文，交回需求分析改未放行稿，或按评审流程退回重评。

## 依据和预期怎么写

预期必须客观、可直接判定通过或失败。来源按优先级取，并在预期或备注里标清类型：

1. 需求原文、知识点、原型或接口文档有写的：优先用，写「依据：」加对应条目或编号。
2. 依据不全、又是敏捷先测的：可以先按实际效果写预期，标「实测归纳：」并写清何时、哪份证据、看到了什么，因此写成这条预期。
3. 需求没写清、也还没测到时：可以脑补预期，必须标「脑补：」并写清思考依据是什么。只能写明确来源，例如同类已有功能、通用交互规则、已经测过的现象、或当前项目里已核实的规则。不得只写「推测」不写理由。

有正式依据的不要改用脑补顶掉。脑补或实测归纳与后来的需求原文不一致时，以需求原文为准，把差异记进待确认，不要暗暗改掉实测记录。资金、撮合、代收代付相关账务判定，不能只靠脑补当上线通过。

依据编号对应知识点号、需求条款或原型位置；只有实测或脑补时，也要在依据编号或备注里写清来源类型和思考依据，不要留空。不明确的地方另记待确认清单，不挡整批已能写、能测的部分。

## 优先级怎么打

每条用例都要在已有的「优先级」字段写下 P0、P1 或 P2，不另加字段，也不要空着。

- P0：核心主链路；或资金安全的主结果，包括入账、出账、余额、手续费入账、对账结果、冲正、回调入账。占到其中一条就是 P0。
- P1：高频使用路径；或资金安全的分支、异常、权限和边界，包括金额临界。
- P2：其余低频、展示、兼容、文案。

同一条里占到更高一档的，整条按更高档打，不要因为「只是边界」打成 P2。非资金需求同样用这三档，核心主链路仍是 P0。

## 怎么做

1. 先看需求分析交来的材料、知识点、场景清单和待确认项。还没有也可以开始写已能确定的主路径用例，不等场景清单评完。
2. 按下面维度逐项扫一遍，缺的记下来，不要脑补一大片没根据的场景，也不要省掉任一维。正向主链路与分支；输入（合法等价类、最小/最大边界、空、空格、特殊字符、超长、格式错误）；权限（角色、无权限、越权、未登录）；操作（重复提交、连续点击、取消、回退、刷新）；异常（超时、下游错误、降级、重试）；数据（空数据、历史数据、关联删除后联动、一致性）；兼容（浏览器、机型、版本、账号状态）。支付与资金类再按下面逐项落用例，不能只在异常维里带过：
   - 幂等：重复提交、重复回调是否只入一笔账。步骤里写清判重条件。没有判重规则就标待确认，不自定一条。
   - 金额：小数位、币种、手续费、限额（最小、最大、恰好临界）和正负金额写进步骤和预期。写死指抄材料或已确认知识点里的原数。没有的数不要编，该条标待确认，覆盖自查里不算已覆盖。
   - 回调与异步通知：超时、重试、乱序、重复通知分开写，各是一个验证点。写清以哪次通知为准。这里的超时和重试指通知本身。
   - 对账与差错：长短款、补单、冲正分开写。各写触发条件和账务结果。
   - 状态：按需求分析交来的状态表写合法迁移和非法跃迁。还没有表时，只写材料里已经点名的状态，不编一轮没出处的状态机，缺的表标待确认。
   - 主从延迟脏读：写清读哪一次查询、在什么时点读。预期写清不能把旧余额或旧状态当成入账依据。没有读口径就标待确认，不自定延迟秒数。
   - 回滚与资金流水一致性：余额、流水、订单的预期要能互相核对。
   适用的维度至少有一条用例。写不清的标待确认后继续写别的条。整维不适用（例如纯接口没有页面）要在覆盖自查写明原因，不写原因的缺项不算扫过。
3. 输出对齐本项目用例库已有字段，不自造字段和状态词。至少要有：正式编号、模块、标题（一句话讲做什么）、优先级、用例类型、步骤要点、预期、依据编号、依据更新时间。前置条件写进步骤要点开头。步骤一步一行，写动作加对象，如「点击【提交】」，不要写「进行提交操作」。
4. 在步骤要点注明哪些走 UI、哪些走接口，不另加字段。能复用的操作或用例要写成复用脚本，脚本要边测边改。
5. 术语用项目里已有的字段名和状态枚举，不自创名词。边界按等价类加边界值来设，并标清等价类。
6. 用例还没定稿也要进库，评审状态写未评审，最近结果写未测；未评审先跑的，结果最高记「已跑待评审」，不算通过，也不算冒烟通过。
7. 一批写完后，单独出一份覆盖自查：按上面维度逐项勾，覆盖了哪些、缺哪些、哪些是脑补或实测归纳、哪些要等确认。已经有用例占位的，写上编号。整维不适用写原因。不要只写「已覆盖」。

## 写完之后

写进本项目用例库并读回一致后，交本项目测试执行按「用例评审」做复核。退回的由需求分析改，改完再送评。
