# 测试证据

一句话：先有证据，再说做完。本技能是证据规则的唯一正文。协作、开工、收工只指向这里，不另定判定标准。

## 不用于

- 派活、接单、记接单／收到成果／验收完成：见 [派工与接单](sand-workflow:skill-1794468373416)
- 出报告、同步测号、释放资源：见 [批次收尾](sand-workflow:skill-1794469727907)
- 外发或写入报告前的脱敏：见 [evidence-hygiene](sand-workflow:evidence-hygiene)
- 写完报告前的抽查步骤可再走 [review-evidence](sand-workflow:review-evidence)，判定仍以本技能为准

## 铁规

1. 没有对得上当前范围、版本、环境的证据，不准说「通过」「做好了」「修好了」「没问题」「都对上了」。
2. 执行人自己的报告不算独立核验。
3. 有变更或上次失败的部分，只补核受影响的地方；没改且上次核验仍然有效的，可以沿用。用户当轮要求回归、复验或重新测试时，不适用本条，必须按第 5 条当场重核。
4. 只报进行到哪的普通进度，不触发全套重验。用户当轮要求回归、复验或重新测试时除外，按第 5 条做。证据撑不住，就照实报现状，不把进度写成完成。
5. 用户当轮说回归、复验、重新测试、再测一遍，或意思相同的话时，必须针对当前范围和当前版本当场重跑、重核，并留下这次的新证据。不准拿以前的截图、报告、结论或「和上次一样」来充当这次的结果。以前的证据只可当作对照，不能当作这次已经测过的证明。没有这次的新证据，不准写通过、修好了或没问题。

## 写通过的门禁

写「通过」前必须同时满足：证据路径非空，评审状态是已放行，依据更新时间不晚于最近执行；高风险还要签字是已签。缺一项写已跑待评审或已跑待确认，不算通过。没有证据的通过一律无效。

## 判定与取证

1. 结论只来自亲眼看到的证据。通过或失败必须挂可核对产物：截图、接口请求响应、控制台、日志、数据库或存储状态。未测、阻塞都写明原因，禁止用「按理说应该」代替验证。
2. 状态只允许：通过、失败、阻塞、未测、未验证；批次进行中还可用已跑待评审、已跑待确认，这两项不算通过。阻塞不等于「我猜会失败」：步骤能执行就跑完记失败加证据；阻塞只用于缺权限、缺数据、环境不可用，并写清已试过的替代路径。
3. 每条检查先定判定信号：点了看什么接口状态、什么界面状态。中途不得悄悄换成更弱的判定；被迫更换就在报告写明原因，结论标部分验证。
4. 缺陷候选先过四道过滤再报：测量工具是否误判（换 curl、换选择器、清 mock 再看）、是否有意设计、基线（改动前或线上同条件）是否本来如此、是否属本次范围。过不了的不报缺陷，写成观察或问题。
5. 反例必须配同条件正例：无效输入报错，只有同会话同表单只改该值的有效输入成功，才算验证通过。正例失败先查正例，反例结论作废。
6. 先怀疑测量工具（选择器、脚本、正则、mock 比产品更容易说谎），意外结果先核对工具与环境是否干净，再怀疑产品。
7. mock 只验证应用反应（不挂死、不误报成功、是否重试），不验证自己塞进 stub 的文案与码；文案、错误码、结构只对真实响应下结论。用完确认 mock 已移除，再用对照请求证明环境干净。
8. 预期来自需求、知识点、原型或规则，不来自当前实现。实现与需求冲突记失败或待确认。
9. 留痕按批次落盘，每批至少记：起止时间、范围、通过标准、通过／失败／阻塞／未测数量、失败摘要、关键证据路径，以及直连还是代理、无头还是有头、用的哪种工具。
10. 跑完先恢复拦截、mock 和改过的数据，并用对照请求证明环境干净。关会话和释放见 [批次收尾](sand-workflow:skill-1794469727907)，这里不重写关浏览器步骤。
11. 列表、排序、筛选防误报（各项目通用，nova 暂停除外）：
    - 先等对应接口返回，确认参数是本次期望值、状态 200、页面首行和响应第 1 条一致，再截图。
    - 用接口返回逐行比对页面，按单元格取值（列的 prop 或单元格标识），不按表头位置目测。
    - 异常先刷新重跑，至少复现两次，每次留 HAR、trace 或接口原始响应。两次都错才判失败，只出现一次写「待复现」，不判失败。
    - 接口证据存原始响应文件或截图，和页面截图放同一用例目录，文件名带时间，不只写文字。没核接口的部分（如另一排序方向）写「未验证」，不跟着判失败。
    - 横向滚动或缩放后的截图不按表头对列；整表图用 100% 并滚回最左，或不滚动的缩小整表图。翻页结论用接口 total 和相邻页首末行比对。并列值不算顺序错误，可记为现象。

## 轻量取证与产物清理

证据规则不变，本节只砍多余取证动作，省时间和资源。各项目通用，nova 暂停除外。

1. 每个关键步骤只留一张截图，配接口关键字段（请求参数、状态码、判定字段）。不每步截多张，不整页、整包抓接口，不录无用屏。
2. 正常通过的结果刷新确认一次就够。复现两次只用于列表、排序、筛选异常（上一节第 11 条）和偶发问题。
3. 复验和回归用已知数据（编号、名称、账号）直接搜索或筛选定位，不翻页扫全表；要看翻页按第 11 条用接口 total 和首末行比对。
4. 资金、撮合、代收代付、上线前等高风险用例不在本节简化范围，取证照原规则做足。
5. 截图和中间产物定期清理，按「留痕」删前四项（含截图、HAR、trace、assets 缓存，缺陷关闭当天可先删中间图，结论包和报告当天不删）。
6. 不把平台截图缓存（如 `/tmp/computer-use`）整包复制进项目目录，只拷本条要用的几张，改成带用例编号和时间的文件名。
7. 新发现的脚本踩坑解决后，脱敏交自动化踩坑知识库。
8. UI 操作前先关掉后台系统已开的旧标签页，只留当前页再搜索或点按钮。旧页签会留隐藏副本，同名按钮出现两个，脚本会误点或超时；定位仍加 `:visible` 兜底。
9. 改数据前先记当前值（截一张或存接口返回），测完恢复后读回比对，对不上马上报。

## 留痕

执行任何测试都要留痕，方便定位问题和写 UI、接口脚本。自己判断记什么，不全量堆砌。

要记：

1. 页面：完整 URL 或路由、菜单路径、进入方式（直开或点进）。
2. 操作：按序写关键步骤，点了什么、输入了什么、等了多久。本地留痕怎么方便怎么记，登录字段和密码也可写入本项目留痕文件，以方便复现和写脚本为准。
3. UI 特征点：优先无障碍名称、role、data-testid、稳定文本，其次 CSS 或 XPath，最后坐标。记下弹层、表格、加载态、空态的判定依据。
4. 接口：方法、路径、关键请求参数、状态码、耗时、关键返回字段、错误码。超时或报错请求必须记。
5. 结果：预期与依据来源、实际结果、截图或录屏路径、环境、账号别名、时间（写明时区）。

不要记：无关静态资源、心跳、埋点；重复且已稳定成功的步骤（写「同上次，无变化」）。发给总控的故障通知、Notion 知识库正文、记忆条目仍不写明文凭证、验证码、token；本地留痕文件不受此限。

处理与清理（7 天清理唯一处；云端同步见 [需求全流程](sand-workflow:skill-1794810862650)）：

1. 留痕放本项目自己的目录，不跨项目混放，每条写日期。本机和云端都不做整盘定时清空。删除单位是一条留痕或一个用例目录，不是 `/workspace/qa/runs/` 整树，也不是整个项目资料夹。日常跑测的 `/workspace/qa/runs/` 不自动全删。账号库、记忆、知识库、技能、周备份包不进这套清理。
2. 路径稳定、会重复跑的，整理成脚本放本项目目录并读回。出问题的先留着，关单后再按下面的删前四项清。一次性探路、没有复用价值的，也要满足删前四项才能删。已转成脚本并读回通过，不能压过「出问题先留着」。
3. 删前四项都要过，缺一项不删：
   1. 允许同步的那部分已经上传并读回；或者已写明只登记位置、本机这份还要留。本机唯一副本在同步成功前不删。
   2. 按缺陷单号或用例编号核对，这一条没有未关缺陷，也没有待复验。同一目录里新旧混放时，只删满足条件的那几条。
   3. 下面三条满足其一，并且不违反第 2 项：已转成脚本并读回通过；或自该条留痕日期起超过 7 天，且没有未关缺陷和待复验；或一次性探路、没有复用价值，且超过 7 天，同样没有未关缺陷和待复验。
   4. 测试日志先写下「清理了哪一条、原因」。日志没写上，不删。
   截图、HAR、trace、assets 缓存等中间产物一并按此删。缺陷关闭当天，该缺陷目录里没进报告、也没进结论包的中间图可以先删。结论包和报告当天不删。
4. 云端用同一套四项。上传没读回，不删云端旧包。Drive 只删已经满足条件的旧包，不整夹清空。资料夹不要放进账号周备份子目录，并和「QA机器人备份」分开，两边都不互相删。
5. 自动化踩坑经验脱敏后交自动化踩坑知识库，不写凭证。
