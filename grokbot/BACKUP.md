# Git 与 Google Drive 备份怎么分

各 Grok Bot 账号共用同一个公开仓库和同一份 Google Drive「QA机器人备份」文件夹。备份子目录按账号名建，不写死账号名单。日常先把共用内容同步到 Git，再按账号把压缩包备份到硬盘。各账号只写自己的子目录。原始文件的周日冻结副本另打共享资料快照，不放进账号周包。见「共享资料快照」。

## 说明放哪

这份说明放在 Git：`grokbot/BACKUP.md`。两边拉同一份仓库，规则就一致。不要只放在硬盘备份包里，免得各写各的、对不上。

硬盘包里的 `RESTORE.md` 只写「本账号怎么恢复」，并指向本文件，包括「恢复与同步检查清单」。不要把整份规则或整份检查清单再抄进包里当正本。

## 干活时的三处正本

规矩和技能读 Git。提炼知识和用例读 Notion 团队空间「幸运小猪-知识海」，从总目录进去。原始文件读 Google Drive「QA项目资料」里的当前文件。压缩包是周日的冻结副本，不是第二天还在改的正本。日常开工不要先解压缩包。

## 账号表怎么查、怎么写

机器人和 Cursor 同一套。正表是谷歌表「测试账号-完整库」。Notion 页「测试账号」是同步写入处，不是查找第一来源。旧表「各项目测试账号与凭证」不再作为官方查找处。表链接不写进本说明。

- 「测试账号-完整库」：正表，放全部账号。
- 「测试账号-给人看」：只给人看，不作为查找第一来源。每域名最多 3 条，用户给的主号优先。

查找：先本地。当前机器是机器人云电脑，读 `/workspace/qa/secrets/qa-test-accounts.md`。当前机器是那台 Windows，读 `C:\Users\青鸟\Documents\qa-test-accounts.md`。当前机器没有这份文件，就查「测试账号-完整库」。找到了直接登录，不弹安全账号、保险库或安全表单。没找到且允许创建，就自己创建后再按云端同步写回。不允许创建就停下说明缺账号，不编造密码，不叫用户去填保险库。

写回只合并补缺：空的不覆盖已填的账号和密码；缺的行补上。写入正表，再写入 Notion 页「测试账号」。碰得到的本地文件合并补缺，碰不到就写明哪一份待补。写完再读一次，账号和密码一致才算完成。测试账密可以写在聊天里。密钥类只记是否存在，不写值。已有的密钥值禁止复制、删除、重置、改值。

人给的账号写入碰得到的本地文件和完整库，并按规则更新给人看的表。大批量生成的测试账号默认只进完整库和碰得到的本地文件。

## Git 里不放什么

- 记忆正文（profile / journal 导出）
- 现网例程的提示词全文打包（例程跟账号走，进硬盘包）
- Drive 备份压缩包本身，包括账号周包和共享资料快照
- 产品原件和知识海导出
- 凭证、表链接、Notion 页面链接、对话链接、邮箱、窗口路径

工作台对话对应关系的正本是谷歌表「QA机器人Cursor工作台」，按账号分页。地址见同步总表与本机指针。不要在仓库里另做一份映射正本，也不要把对话链接写入 Git、规则包或本说明。

两边对齐技能和职责：拉仓库，有改动就开 PR。不要用周包、增量包或 skill-sync 包覆盖仓库里的技能副本，也不要覆盖现网技能。仓库技能以现网为准，改完再回写仓库。跨账号只对照技能 id，不把对方的技能 id 写成本账号已经接上。

## 硬盘包里放什么

每个账号每周日做一次完整备份，传到：

`QA机器人备份/<账号名>/qa-backup-weekly-<账号名>-<YYYYMMDD>.zip`

这份包只管换号、换电脑时恢复这一个机器人：记忆、例程、角色资料、那一刻的交接。产品说明和需求原包不放进这个包。

账号名用这个 Grok Bot 账号当时的名字。没有同名子目录就新建。只写、只恢复自己的子目录。不改、不删其他账号的子目录，也不动根目录下其他账号的文件。同步时读来源账号目录里的最新完整备份，并查较新的增量包或 skill-sync 包，用来核当前账号自己的工作台。步骤见「恢复与同步检查清单」。来源和当前谁是谁，按当次决定，不写死账号名。

每周日打一次完整包。打包时和上一包对比，核对校验值，写出变更记录和清单。旧包不删除，在原文件名前加 `已替换-`。失败时保留旧包并说明。

包内另放两份只读材料：规则包镜像（文件名带版本），以及一句指针「规则包正本在 Git，恢复时不覆盖」。工作台表快照同样只读，恢复时不覆盖谷歌表里更新的映射，并且不把对话链接写进 Git。

包里只放：

- 本账号能读到的记忆导出（自己的和共享的 profile / journal）
- 本账号机器人名单（名字、标题、描述和对应 json）
- 本账号例程（名字、时间、提示词）
- 本账号的恢复说明 `RESTORE.md`
- 技能文件夹快照（只作本账号当时的副本，对账以 Git 为准）
- 环境脚本、近 30 天 snapshots、用户上传的文档（按例程限制）
- 备份那一刻的交接，放在压缩包根目录。默认一份 `WORK-STATUS.md` 或 `交接.md`，含下面六项。拆成短清单时，每一份都要在这个包里
- 很短的 `SOURCES.txt`，只写本周共享快照的文件名、日期和清单校验。不写产品正文，不写别的账号的记忆

技能和角色的共同来源是 Git。硬盘包里的技能只是当时快照，恢复时先拉仓库，再按需看包里有没有尚未回写仓库的改动。不能用仓库原文直接覆盖现网技能 id。

包里四块：

- `files/`：资料夹的文件副本
- `export/`：知识海的文字导出
- `catalog.jsonl`：清单，一行一条
- `GAPS.md`：本周对出来的缺口

包根写一小段：这是冻结副本；要最新的，打开 Notion 和资料夹。

已经在「QA项目资料」里的产品说明和需求原包，每次全文进快照，不再由人判断这周还用不用。产品说明、规格、操作手册、页面说明、HTML 手册全文进「QA项目资料」，并进这份快照。

测试跑出来的截图、HAR、跑次日志不进共享快照。需求流程里这种大包默认同步时不上传，只登记位置。不要把「大包不上传」理解成产品说明也可以只登记路径。

知识海导出只含知识点、用例、系统地图和资料索引。每日测试日志留在 Notion。账号资料页不导出。缺陷留在知识海，不进这份导出。不把整包原文件塞进知识库页面。每日约 23:30 的巡检照旧，只看当天知识库有没有存档。M3、支付停工期间跳过，nova 跳过。

测试登录账密不进周包，也不进共享快照。密钥类只记有没有，正文不进包。聊天记录、`store.db`、附件原文仍不进任何包。小程序不收。

旧的共享快照先按周包同样办法留着，一份都不删。等打出两份、看过体积之后，再决定旧的全文包能不能只留清单。点头之前不删。不删任何 Drive 旧包。

`GAPS.md` 只用白话写三小段：只有文件还没写进知识库的；知识库点了名但原件不在的；这周没能导出的提炼知识。没有就写「无」。缺口不自动写进 Notion。

清单是这套方案的目录。资料夹里的非密钥文件每次都打进同一份共享快照，不是必要时再打旁路包。

### 清单

清单一行一条，用 jsonl，方便脚本和 AI 逐行读。每行这些字段都要有：

- 项目
- 种类：原始文件、提炼知识、用例，或交接
- 标题
- 包内路径
- 资料夹里的相对位置：写相对路径，不把完整链接写进 Git
- 内容校验
- 字节数
- 它引用了哪些原始文件
- 哪些知识或用例引用了它
- 状态：在用、只有文件未入库、知识指了但原件缺失、暂停只收不写库
- 日期
- 是否密钥类。标了「是」的，这一行只表示存在，包里没有正文

### 三遍对照

周日打包时做三遍对照，不靠人回忆。

第一遍扫「QA项目资料」里的文件。密钥类文件不收正文，只留清单上的「有」。其余每个文件都要有清单行。没有任何知识或用例引用它的，状态写成「只有文件未入库」。这不是失败，文件已经在快照里，不会丢。它只是提醒知识库总控：这条要不要提炼。不自动往 Notion 写。

第二遍扫知识点和用例上写的依据。点名的文件必须在清单里，也必须在 `files/` 里。对不上的写成「知识指了但原件缺失」。

第三遍只问在用项目一句：有没有产品说明还只在聊天或本机，没放进资料夹。答案写进 `GAPS.md`。总控不把聊天附件自动拖进包，里面可能夹着密钥。确认是产品说明之后，放进资料夹，下一次快照才收。

暂停项目不叫醒、不写库、不测试。资料夹里已经有的文件仍收进快照，状态写暂停。GO 在知识库入口未定之前不导出、不写库，文件仍可收。小程序不进这套。

### 先读哪份

日常开工不要先解压缩包。先读 Git 里的接手说明和本文件，再读知识海总目录。原始文件以资料夹当前文件为准。

换号、换云电脑，或者怀疑有文件没入库时，先读本账号最新周包里的 `RESTORE.md` 和 `WORK-STATUS.md`，再按 `SOURCES.txt` 打开那份共享快照，先读 `catalog.jsonl`，再按里面的路径打开文件或导出稿。

## 记忆不要自动对倒

记忆是各账号自己的工作记录。要看对方记了什么，打开来源账号子目录里最新的完整包，对着看，列出差异，用户点头后再改自己这边。最新完整包可能旧于同一目录里较新的增量包或 skill-sync 包，也可能旧于现网工作台。要看规则、技能、角色说明、协作规范和工作台时，按「恢复与同步检查清单」把这些来源一起读，并核当前账号自己的工作台。记忆、例程和机器人资料仍然不对倒。禁止两边定时互相同步记忆，也不要做自动解除冲突。工作台核实缺失后的补齐不套用「等用户点头」。
