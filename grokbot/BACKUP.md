# Git 与 Google Drive 备份怎么分

各 Grok Bot 账号共用同一个公开仓库和同一份 Google Drive「QA机器人备份」文件夹。备份子目录按账号名建，不写死账号名单。日常先把共用内容同步到 Git，再按账号把压缩包备份到硬盘。各账号只写自己的子目录。

## 说明放哪

这份说明放在 Git：`grokbot/BACKUP.md`。两边拉同一份仓库，规则就一致。不要只放在硬盘备份包里，免得各写各的、对不上。

硬盘包里的 `RESTORE.md` 只写「本账号怎么恢复」，并指向本文件，包括「恢复与同步检查清单」。不要把整份规则或整份检查清单再抄进包里当正本。

## 三处各放什么

| 放哪 | 放什么 | 谁用 |
|--------|--------|------|
| Git 仓库 qa-agent-team 的 `grokbot/` | 角色说明、花名册、共用技能的脱敏副本、协作规范、本说明、常驻规则包 | 各账号都拉、都按这个对齐 |
| Google Drive「QA机器人备份」 | 按账号分开的周备份压缩包，用来恢复「这一个 bot 账号」 | 各账号只写自己的子目录 |
| 各项目 Notion 知识库 | 业务知识、用例、缺陷、测试日志 | 不进 Git，也不进硬盘压缩包 |

token、密钥类、Cookie、.env：三处都不写。测试账密明文可以进 Git 和文档。查号和写回见下文「账号表怎么查、怎么写」，步骤与 `grokbot/HANDOFF.md`「测试账号在哪」同一套。

## 账号表怎么查、怎么写

机器人和 Cursor 同一套。正表是谷歌表「测试账号-完整库」。Notion 页「测试账号」是同步写入处，不是查找第一来源。旧表「各项目测试账号与凭证」不再作为官方查找处。表链接不写进本说明。

- 「测试账号-完整库」：正表，放全部账号。
- 「测试账号-给人看」：只给人看，不作为查找第一来源。每域名最多 3 条，用户给的主号优先。

查找：先本地。当前机器是机器人云电脑，读 `/workspace/qa/secrets/qa-test-accounts.md`。当前机器是那台 Windows，读 `C:\Users\青鸟\Documents\qa-test-accounts.md`。当前机器没有这份文件，就查「测试账号-完整库」。找到了直接登录，不弹安全账号、保险库或安全表单。没找到且允许创建，就自己创建后再按云端同步写回。不允许创建就停下说明缺账号，不编造密码，不叫用户去填保险库。

写回只合并补缺：空的不覆盖已填的账号和密码；缺的行补上。写入正表，再写入 Notion 页「测试账号」。碰得到的本地文件合并补缺，碰不到就写明哪一份待补。写完再读一次，账号和密码一致才算完成。测试账密可以写在聊天里。密钥类只记是否存在，不写值。已有的密钥值禁止复制、删除、重置、改值。

人给的账号写入碰得到的本地文件和完整库，并按规则更新给人看的表。大批量生成的测试账号默认只进完整库和碰得到的本地文件。

## Git 里不放什么

- 记忆正文（profile / journal 导出）
- 现网例程的提示词全文打包（例程跟账号走，进硬盘包）
- Drive 备份压缩包本身
- 凭证、表链接、Notion 页面链接、对话链接、邮箱、窗口路径

工作台对话对应关系的正本是谷歌表「QA机器人Cursor工作台」，按账号分页。地址见同步总表与本机指针。不要在仓库里另做一份映射正本，也不要把对话链接写入 Git、规则包或本说明。

两边对齐技能和职责：拉仓库，有改动就开 PR。不要用周包、增量包或 skill-sync 包覆盖仓库里的技能副本，也不要覆盖现网技能。仓库技能以现网为准，改完再回写仓库。跨账号只对照技能 id，不把对方的技能 id 写成本账号已经接上。

## 硬盘包里放什么

每个账号每周日做一次完整备份，传到：

`QA机器人备份/<账号名>/qa-backup-weekly-<账号名>-<YYYYMMDD>.zip`

账号名用这个 Grok Bot 账号当时的名字。没有同名子目录就新建。只写、只恢复自己的子目录。不改、不删其他账号的子目录，也不动根目录下其他账号的文件。同步时读来源账号目录里的最新完整备份，并查较新的增量包或 skill-sync 包，用来核当前账号自己的工作台。步骤见「恢复与同步检查清单」。来源和当前谁是谁，按当次决定，不写死账号名。

每周日打一次完整包。打包时和上一包对比，核对校验值，写出变更记录和清单。旧包不删除，在原文件名前加 `已替换-`。失败时保留旧包并说明。

包内另放两份只读材料：规则包镜像（文件名带版本），以及一句指针「规则包正本在 Git，恢复时不覆盖」。工作台表快照同样只读，恢复时不覆盖谷歌表里更新的映射，并且不把对话链接写进 Git。

包里只放：

- 本账号能读到的记忆导出（自己的和共享的 profile / journal）
- 本账号机器人名单（名字、标题、描述和对应 json）
- 本账号例程（名字、时间、提示词）
- 本账号的恢复说明 `RESTORE.md`
- 技能文件夹快照（只作本账号当时的副本，对账以 Git 为准）
- 环境脚本、近 30 天 snapshots、用户上传的文档（按例程限制）
- 备份那一刻的交接，放在压缩包根目录。默认一份 `WORK-STATUS.md` 或 `交接.md`，含下面六项。拆成短清单时，每一份都要在这个包里

技能和角色的共同来源是 Git。硬盘包里的技能只是当时快照，恢复时先拉仓库，再按需看包里有没有尚未回写仓库的改动。不能用仓库原文直接覆盖现网技能 id。

## 备份那一刻的工作点交接

2026-11-17 用户确认。这是备份流程约定，正本在本仓库本文件，不是平台 Auto-review，也不是 AI 规则。做备份的步骤见 `grokbot/skills/account-backup/SKILL.md`。各项目知识库的每日存档走日备读回，和本节不是同一件事，不互相替代。

以后做本账号完整备份时（包括每周日的周备份，以及换号用的全量备份），必须按「备份的那一刻」写清各项目、各工作点正在做的事，并写上下面六项。默认写进同一份交接文件。拆开时，每一份都要进包。`MANIFEST.md` 和 `RESTORE.md` 都要写明这些文件的名字和在包里的位置。

交接的目的：另一边拿到备份后，马上知道已经做了什么、接下来要做什么、去哪里查看。用户让他们做事时，也能立刻找到入口。几个账号同步时，记忆、例程和机器人资料对上看、列出差异，等用户点头再改，不要自动覆盖对方已有内容。当前账号工作台核实缺失后的补齐，不套用这句等待，见「恢复与同步检查清单」。

六项都要有：

1. 已经做了什么、接下来要做什么、去哪里查看。去哪里查看包括：对应该项目这个工作点的机器人聊天入口、缺陷单、用例页、知识库入口、HTML 报告、跑次目录、本地未写库的稿、工作台映射位置（谷歌表「QA机器人Cursor工作台」里`工作台-<当前账号>`和`派单记录-<当前账号>`；这次有来源账号时，写上`工作台-<来源账号>`和`派单记录-<来源账号>`，并写核对日期。地址见同步总表与本机指针。仓库映射里已有的账号名只是例子，不写死方向）。这些地址写在周包内的交接里，不写入本说明。对话链接不写入本说明，也不写入 Git。未核验通过的旧协调器 id 不写成可用。
2. 待用户拍板的事。
3. 连接器与账号标签清单：已接哪些、哪条未授完。只写名称和状态，不写 token，不写凭证表链接。
4. 仓库未合变更与现网差异：打开的 PR、草稿 PR、现网技能版本和技能 id 与仓库的对照。必须写明：换号后只拉 main 可能漏掉未合内容；不能直接用仓库原文覆盖现网技能 id。
5. 机器人角色对照：角色名、当时 id、是否已删除。必须写明：换号后 id 会变，先按角色建号，不要按旧 id 把已删的号重建回来。
6. 进行中产物索引：见第 1 项，不另抄一套。

写法：

- 按项目分节，至少包括 T8T、M3（含支付与重粉库）、GO。nova 在花名册是暂停时，该节只写「暂停，跳过」。小程序由用户自管，总控不管，该节只写这一句。
- 每个在用项目里再按工作点写第 1 项。工作点以备份当时花名册里该项目实际有的号为准，例如需求分析、测试主管、测试执行、站点走查、提单回归、知识库总控、日报、周报，以及当时仍在用的专项号。没有在测任务的工作点写「当前无在测任务」，不要省略该工作点。M3 的支付和重粉库分开写入口和现状，不拿一套代替另一套。
- 第 1 项里把正在测什么、卡在哪、等谁、未关缺陷写进「已经做了什么」和「接下来要做什么」。六项都只写备份那一刻能核实的事实。不要用旧截图、旧结论或猜测写进度。没有当轮能核实的事实就写「未核到更新」，不要编造链接、进度、PR、技能 id 或角色 id。
- 不写 token、密钥类的值、Cookie、凭证表链接、聊天全文、`store.db`。测试账密明文可以写。可以写测号名称、环境、缺陷库链接、报告路径。

这份交接是给另一账号或新总控对照用的。`RESTORE.md` 要写清：记忆、例程和机器人资料对上看、列出差异、等用户点头再改。不要用这份交接自动覆盖对方已有的记忆、例程、机器人资料和其他已有内容。当前账号工作台的补齐见「恢复与同步检查清单」，不套用这句等待。

## 记忆不要自动对倒

记忆是各账号自己的工作记录。要看对方记了什么，打开来源账号子目录里最新的完整包，对着看，列出差异，用户点头后再改自己这边。最新完整包可能旧于同一目录里较新的增量包或 skill-sync 包，也可能旧于现网工作台。要看规则、技能、角色说明、协作规范和工作台时，按「恢复与同步检查清单」把这些来源一起读，并核当前账号自己的工作台。记忆、例程和机器人资料仍然不对倒。禁止两边定时互相同步记忆，也不要做自动解除冲突。工作台核实缺失后的补齐不套用「等用户点头」。

## 用户说「同步」

同一账号日常说「同步」：把尚未回写仓库的共用改动开 PR，总控不自己合并。不跑下面的换号清单。

换到新 Grok Bot 账号或新机器后，或用户要求把一个账号的工作台同步到另一个账号时，按固定顺序做。接收的一方是当前账号，提供备份或映射的一方是来源账号。方向不写死。拉完 Git 不算同步完成。是否恢复完成，看「恢复与同步检查清单」。

1. 拉取公开仓库 qa-agent-team，按 `grokbot/HANDOFF.md` 安装技能，按花名册认当前账号自己的机器人。换号后机器人 id 可能变化。不把来源账号的机器人 id 或技能 id 抄过来当成当前号。旧账号机器人停用，也不等于该账号里已有的 Cursor 对话失效。
2. 读 `grokbot/cursor-resident/PACK.md` 首行版本，和本机指针里的已装版本比较。地址见同步总表与本机指针。版本相同则不写规则包。任何情况下都不用周包、增量包或 skill-sync 包覆盖 Git 里的规则包，也不覆盖现网技能。当前账号补自己的工作台映射，见检查清单，不借这次同步改认正本。
3. 重新连接 Notion、Google Drive、GitHub 等连接器。连接器授权、云电脑登录态、Cookie 不能从备份恢复，必须由用户重新点授权、重新登录。
4. 恢复当前账号的记忆和例程：只打开`QA机器人备份/<当前账号>`里最新的周备份包，按包内 `RESTORE.md` 贴回当前账号。没有同名子目录就新建。不把来源账号的记忆贴回来。不改、不删来源账号的子目录。
5. 核工作台并补齐：按「恢复与同步检查清单」读来源账号目录的最新完整备份，并查较新的增量包或 skill-sync 包。读规则、技能、角色说明、协作规范、工作台映射。再看`工作台-<当前账号>`、`派单记录-<当前账号>`，需要对照时看`工作台-<来源账号>`、`派单记录-<来源账号>`。当前账号逐个核对自己现有机器人应有的工作台。核实缺失的按清单补上并读回。不覆盖来源账号的记忆和技能。
6. 运行云电脑上的 qa-ready.sh，不要默认跑 bootstrap 或 apt。
7. 查号和写回按本文件「账号表怎么查、怎么写」。机器人和 Cursor 都先找本地，没有再查谷歌表「测试账号-完整库」。聊天可以写测试账密。密钥类、token、Cookie 不进 Git，也不打进备份包。周备份包可以不重复打包测试账密（云端和仓库已有即可，是否再打进周包待用户另定）。
8. 不要恢复完整聊天记录、`store.db`、附件原文。业务记忆点以各项目 Notion 知识库为准。账号记忆以周备份里当前账号的记忆为准。验收缺清单里的任一项，结论写未完成。只找到来源账号的映射，不算同步完成。

## 恢复与同步检查清单

换号、换机器，或把一个账号的工作台同步到另一个账号时，用这一节验收。接收的一方是当前账号，提供备份或映射的一方是来源账号。同一账号日常只说「同步」、意思是把共用改动开 PR 时，不跑这一节。

Git 拉完不算同步完成。只找到来源账号的映射，也不算同步完成。清单里缺一项，结论写未完成。

仓库映射里出现过的账号名只是例子，不规定只能从某一个账号同步到另一个账号。

### 正本冲突先挂起

本清单不裁决正本。仓库里有两套说法。一套写工作台正本是谷歌表「QA机器人Cursor工作台」，Git 不另做映射正本，见本文件前文、`grokbot/cursor-resident/PACK.md` 和同步总表技能。另一套写正本是 `grokbot/workbench-map.md`，谷歌表只是同步副本，见 `grokbot/HANDOFF.md`、`grokbot/workbench-map.md`、`grokbot/skills/project-bot-collab/CURSOR-WORKBENCH.md`。两套都读。按日期和来源列出差异，等用户确认后再改认正本。不自动解除冲突，不覆盖来源账号的记忆，不覆盖现网技能。补当前账号自己的工作台，不借这次补齐把另一处改认成副本。

### 来源

1. 拉取 Git。读规则、`grokbot/skills/` 里的技能副本、`grokbot/cursor-resident/` 里的规则和技能、角色说明、协作规范、`grokbot/workbench-map.md`。这只是来源之一。记下提交号。
2. 读 Google Drive`QA机器人备份/<来源账号>`里最新完整备份，按包内 `RESTORE.md` 对照。记录包名、更新时间、账号。当前账号的记忆仍只从`QA机器人备份/<当前账号>`贴回。
3. 来源账号同一目录里，比该完整包更新的增量包或 skill-sync 包也要读。完整包可能落后于这些包，也可能落后于现网工作台。
4. 从包里读规则、技能、角色说明、协作规范、工作台映射。记下源文件、更新时间、账号。技能快照只对账。跨账号技能 id 对照着写。不用仓库原文、周包或 skill-sync 包覆盖现网技能 id，也不把来源账号的技能 id 写成当前账号的。
5. 密钥类、token、Cookie、凭证表链接不进 Git，也不打进备份包。验收记录里不抄密钥类的值。测试账密可以进 Git 和聊天。发现密钥类的值要进 Git 或备份包就停，不上传。

### 工作台核谁

打开谷歌表「QA机器人Cursor工作台」。地址见同步总表与本机指针。

当前账号看`工作台-<当前账号>`和`派单记录-<当前账号>`。需要对照来源时，再看`工作台-<来源账号>`和`派单记录-<来源账号>`。三种入口都要核：角色主对话、需求或主题子对话、Project 协调器。

下面任一项都不能单独用来断言入口缺失：当前账号页是空的、仓库里的旧快照、旧机器人停用标签、当前账号的 Projects 列表没有记录。机器人停用或换号后 id 会变，不等于已有的 Cursor 对话失效。仓库快照可能旧于表和较新的包。

无权限或找不到，不是「已确认缺失，可以重建」。写成访问阻塞。

### 三种入口

- Project 协调器。按该账号已核实的协作规则路由。共用框架、云电脑脚本、机器人协同走对应的共用协调器。业务由该项目主管对接该项目的协调器。
- 角色常驻，也就是主对话。
- 需求或主题子对话。

角色常驻和需求子对话不顶替协调器。协作细则见 `grokbot/skills/project-bot-collab/CURSOR-WORKBENCH.md`，本清单不另抄派工步骤。

花名册或用户标明暂停的项目，只核离线映射。不唤醒、不派工、不测试、不建工作台。花名册仍以 `grokbot/bots/roster.md` 为准，本清单不改花名册。现有规则不要求工作台的角色，例如只出报告的日报、走查、周报，以及壳号，不硬建。

### 核实缺失就补

先查已有映射和已经存在的窗口。匹配当前账号这个机器人的身份和职责。能复用原来的工作台，就复用，缺的映射补上。窗口已经在，只是映射缺了或指错了，就补映射或改正，不另开窗口。

确实还没有窗口，并且现有规则要求这个角色有工作台：按规则建立正确类型，登记，再按原页、原行读回。角色主对话，以及规则已经要求存在的需求或主题子对话，按这条补。不批量重建。不把来源账号的机器人 id 或技能 id 抄过来冒充当前账号。

2026-11-20 用户授权把「核实缺失就补上」写进本说明。补当前账号自己的映射，以及按现有规则应有的工作台，不需要每条再等一次确认。

访问、JoinProject、新建 Project、发送，仍走工具自己的权限，不能绕过。需要 JoinProject 时，必须先有用户当轮明确允许。拒绝后如实写「不存在，或当前账号没有该团队权限」，不判定是哪一种。写明未加入、未发送。等待有效的分享入口或授权。不换 id 试探，不绕过权限，不另开一个窗口或另建一个 Project 来代替进不去的那个。只有实际确认之后，才写加入成功、发送成功或设置成功。未经当前账号核验通过的旧协调器 id 不写成可用，也不写死进仓库。

补映射写到当前账号自己的`工作台-<当前账号>`和`派单记录-<当前账号>`。正本在表还是在 Git，仍等用户确认。确认之前，写进这次同步实际在用的那一处，验收里写明写了哪一处。不改来源账号的页。不覆盖来源账号的记忆和技能。

### 验收才算恢复完成

下面都要有。每一条都按当前账号自己的机器人来写，不用来源账号的名单代替。

1. 来源和时间对照：Git 提交、来源账号与当前账号的最新完整包、较新的增量包或 skill-sync 包、工作台表。每项写源文件或包名、更新时间、账号。
2. 规则和技能差异清单，含跨账号技能 id 对照。没有差异写「已对照，无差异」。不把来源技能 id 写成当前账号已接上。
3. 当前账号每个现有机器人、每个按规则应有的窗口：核验结果写「可访问且可续聊」「已补并读回」「本就不该有工作台」「访问阻塞」或「未核到」。已补的写补了什么、写到哪一处、读回是否对得上。
4. 未解决的阻塞。JoinProject 被拒时写「不存在或无团队权限」、未加入、未发送。这类不是已确认缺失，不重建。
5. 仍未同步的其他项。包括等用户确认的正本冲突、未覆盖的现网技能、未对倒的来源账号记忆。

本说明只规定接手者执行同步时怎么核、怎么补。这一次改仓库说明，不批量改现网工作台，也不改谷歌表。

## Cursor 对话怎样同步和恢复

每个机器人对应哪条 Cursor 对话，本文件原有说法是：正本是谷歌表「QA机器人Cursor工作台」，按账号分页。与 `grokbot/workbench-map.md` 不一致时，不在恢复时自动改认，见「正本冲突先挂起」。现在查、写当前号用本账号那一页。地址见同步总表与本机指针。不要在仓库里另做一份映射正本，也不要把对话链接写入 Git、规则包或本说明。

对话正文在 Cursor 后端。同一个 Cursor 账号打开映射里的原对话，就可以接着聊。这是 Cursor 自己的保存，不是周包。

恢复对话按「恢复与同步检查清单」做完才算完成。先拉 Git 只是来源之一。规则包仍不让周包覆盖。当前账号的记忆只从当前账号的周包贴回。工作台先核`工作台-<当前账号>`。需要对照时再看`工作台-<来源账号>`，以及来源账号目录里的最新完整包和较新的增量包或 skill-sync 包。这些包里的规则镜像和表快照，只在 Git 或现网表暂时拿不到时对照，不覆盖 Git 里更新的规则包，不覆盖现网技能，也不覆盖来源账号的页。核实缺失的工作台按检查清单补上并读回。然后只续当前账号上已经核实能打开的原对话。

对话打不开、已过期或无法继续时，沿用工作台已有规矩：旧地址记入「上一条」，旧行改为停用，再开新对话。不把来源账号的对话拿来当当前号续聊。三种入口和 JoinProject 见检查清单，这里不另写。

换了一个新的 Cursor 登录时，旧对话不会跟着仓库或周包过来。映射只说明从前哪条对话属于哪个机器人。新开对话后改当前账号自己的工作台页。不复制来源账号的对话，也不对倒来源账号的记忆，也不把来源账号的机器人 id 当成当前号。

周备份目录是`QA机器人备份/<账号名>`。账号名用这个 Grok Bot 账号当时的名字，不写死名单。没有同名子目录就新建。只写、只恢复自己的子目录。读来源目录是为了核当前账号的工作台，不写回来源目录。

云电脑磁盘快照闲置超过 30 天会清除。恢复对话和规矩都不依赖快照。
