# 用例复核

2026-11-21 用户原话。没有特殊说明就按本技能做。正本是 `grokbot/skills/case-review/SKILL.md`。下面规则与正本同一句，不另定口径。不新建安装 id。未合并进 Git 前，不按这一版安装。

## 停手

1. 用户当轮明确说这次不用 Cursor 复核：跳过。没说就做。
2. GO：本技能停手，不扩用例生成与评审。
3. M3、支付、nova 暂停期间：不派、不叫醒、不写库。
4. 小程序不进这套。
5. Cursor 复核时：不点页面，不跑测试，不写通过或失败，不改用例库，不开 PR，不合并 PR。

## 什么时候做

1. 用户给需求后：需求分析开始写用例。需要对照文档理逻辑、写完整用例时，仍交该号「需求分析」Cursor 对话，规则见 `grokbot/skills/workbench-fill/SKILL.md`。测试执行可以同时开工，先冒烟，再测已经写出来的其他用例。不必等全部用例写完，也不必等评审全部过完。
2. 机器人把一批用例设计好并写入本项目 Notion 用例库后，评审状态仍是未评审：默认把这批可执行用例交给 Cursor 复核。
3. 在用项目按此执行。当前主要是 T8T。

## 交给哪条对话

1. 走该项目测试执行号的常驻工作台对话。不走写这批用例的需求分析对话。
2. 同一项目、同一需求标识的复核续同一条常驻对话。不新开「用例评审」用途行。
3. 日报、走查、周报仍不建工作台。
4. 该号还没有常驻、且这是第一笔思考活时，才按工作台填空建常驻行。

## 谁发简报

本项目测试执行（评审人）发简报。需求分析写好库并读回后，把用例页标题、编号清单和依据交给执行号。执行号按工作台填空发复核简报。任务写复核。八项简报仍要齐。要的交付物是建议放行、退回改、待核实（缺依据），以及逐条或按编号的理由。总控只转达，不代写简报，不代评，不代测。

## Cursor 怎么复核

Cursor 复核只做对照：步骤是否可执行，预期是否和依据一致，有没有漏关键点，有没有超出范围，依据是否齐全。结论只用：建议放行、退回改、待核实（缺依据）。逐条或按编号列出理由。不点页面，不跑测试，不写通过或失败，不改用例库，不开 PR，不合并 PR。简报禁做仍带工作台填空那六句：不点页面，不跑业务测试，不写测试结论，不写凭证，不开 PR，不合并 PR。

## 拿回之后

测试执行自己核一遍，再写评审状态：已放行、待核实、建议删除。Cursor 原文不直接抄进用例库。退回的交需求分析改。改完仍回同一条测试执行常驻对话再复核，不新开。

## 和测试并行

1. 冒烟和其他执行不等 Cursor 复核完，也不等全部已放行。
2. 未评审先跑的，结果最高记「已跑待评审」，不算通过，也不算冒烟通过。
3. 复核并由评审人写成已放行后，用已有证据对照。只有用例改动影响判定的才补跑。
4. 写「通过」的门禁不变：证据路径非空，评审状态是已放行，依据更新时间不晚于最近执行。高风险还要签字已签。缺一项仍写已跑待评审或已跑待确认。

## 低风险

低风险且测试点不超过 5 的：仍由测试执行兼评审，不过主管，不过总控。默认仍要先走 Cursor 复核，除非用户当轮说这次不用。

## 不降级

资金、撮合、代收代付、上线不降级、不跳步。总控第二签字规则不变：只对已放行的高风险核依据和证据。签字和冒烟并行，不挡开测。签字前的结果不进上线结论。已跑待确认不能写成上线通过。其余取值见协作「用例分批放行」，这里不另定。
