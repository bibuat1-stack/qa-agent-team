# Playwright 最佳实践

只讲怎么把脚本写稳。探路优先级看 box-ui-speed。失败和不稳定用例看 e2e-debugger 和 playwright-report-triage。无障碍加深看 accessibility。画布页看 canvas-ui-testing。

## 定位

优先：角色和可访问名、标签、测试标识。其次稳定的 id 或 name。最后才是样式或坐标。定位器可自愈：只换更稳的同意图定位（优先 role / testId）。

不要用会随构建变化的类名当唯一依据。列表和表格按单元格标识取值，不按表头像素目测。

## 等待和断言

用断言的自动等待，不写固定睡眠。断言必须能红能绿：失败时测试失败，成功时测试通过。

不把加长超时、强制点击、跳过或删掉断言当成修复。

预期来自已确认知识点、契约或当次任务依据。没有依据的断言标待确认，不当通过依据。

动作后先验业务结果：该跳到哪、金额和状态对不对、关键文案是不是预期的；控件 enabled/hidden 可作补充，不能单独拿「某个控件还在」或「按钮消失了」代替业务结果。

断言按依据改：需求已经写明或属于资金账务时，页面不符就是缺陷，不得为了跑绿改断言、删断言或放宽断言。需求没写清，又不是资金账务或需求里已经写明的点时，可按页面实际改断言，必须标明「实测归纳」并写清思考依据，先改用例和断言再重跑，不能在当次失败里悄悄把期望改成现状就算通过。资金账务不能只靠页面现状当成上线通过。需求已明确变更时，同样先改用例和断言再重跑。

## 结构回归和截图回归

关键区域可以用无障碍快照断言钉住结构。像素截图只用于受控画面，遮住时间、余额、动画等会变的区域。没有基线就写未验证，不静默写通过。

## 隔离

每个项目的脚本和登录态分开。不混用两个项目的选择器。脚本放在仓库约定目录，读回后再算落盘完成。会推到 GitHub 的脚本不写明文账号、密码、令牌。
