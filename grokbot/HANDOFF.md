# 接手说明

另一套 Grok Bot 拉下本仓库后，按本文件接手。先看结论，再按步骤做。

新 Grok Bot 接手时读 `grokbot/MEMORY-EXPORT.md`。里面是已存储的指令、身份、职业、项目和偏好。

## 仓库放什么

本仓库放这些：

- 角色说明：`grokbot/bots/`。在用角色以 `grokbot/bots/roster.md` 为准。
- 共用技能备份：`grokbot/skills/`。
- 自动化框架：用例、页面、配置和执行入口。写法见根目录 `AGENTS.md`。
- 协作规范：本文件、`grokbot/README.md`、`grokbot/skills/project-bot-collab/`。
- 工作台映射：`grokbot/workbench-map.md`。按账号分页，页名是`工作台-<账号名>`和`派单记录-<账号名>`。文件里已有的账号名只是例子，不规定同步方向。查、写进当前账号自己的页。正本在本文件还是在谷歌表，见 `grokbot/BACKUP.md`，本文件不另改认。
- 备份分工：`grokbot/BACKUP.md`。Git 与 Google Drive「QA机器人备份」各放什么。恢复与同步的检查清单也在该文件。Git 拉完不算同步完成。

云电脑共用脚本的备份在 `tools/cloud-computer/`（`qa-ready.sh`、`bin/box_health.py`、`bin/html_report.py`，以及浏览器默认脚本 `bin/browser_defaults.py`、`bin/open_direct_headed.py`、`bin/README-browser.md`）。云电脑上仍运行 `/workspace/qa/qa-ready.sh` 和 `/workspace/qa/bin/` 里的同名文件。UI 回归默认无头；有头窗口默认 1920×1200。不要改平台桌面 Chrome，也不要改 8791。方案正文不进 Git。登录态、租约、测号和代理密码也不进 Git。

业务知识在各项目 Notion。业务知识不在 Git。

## 不放什么

下面这些不进 Git，也不写进技能正文或映射正本：

- 凭证
- 密码、token、密钥
- 测号密码
- 凭证表链接
- 记忆正文
- Drive 备份包和 nova 备份
- 连接器登录态

工作台的对话地址和对话 id 可以进 Git，只写在 `grokbot/workbench-map.md`。2026-11-12 用户原话：「谁说不能进的，git那保存这些又没关系」。此前写过对话地址、对话 id 不进 Git，以这句为准。

## 新 Bot 接手步骤

1. 克隆本仓库。
2. 按 `grokbot/skills/` 导入共用技能。`grokbot/skills/project-bot-collab/CURSOR-WORKBENCH.md` 是工作台规范，用来补现网技能，不用它覆盖现网 `SKILL.md`。映射正本读 `grokbot/workbench-map.md`。
3. 按 `grokbot/bots/roster.md` 建角色。`bots/` 里早期四份模板保留作对照。实际项目机器人以花名册为准。
4. 在云电脑第一次重建工具链时运行 `tools/bootstrap_bot_computer.sh`。日常开工不要跑它，也不要跑 apt；运行 `/workspace/qa/qa-ready.sh`。用户对总控只说「同步」时，按下一节的固定顺序，不默认跑 bootstrap。这份脚本的仓库备份在 `tools/cloud-computer/qa-ready.sh`，体检、批次 HTML 报告和浏览器默认脚本的备份在同目录 `bin/`。体检低于 2048 MiB 时只提示，退出码仍是 0。
5. 重新授权 Notion、Google、GitHub 等连接器。连接器登录态不会随仓库过来。
6. 测试账号不在仓库。去哪找、先看哪一份、怎么同步，见本文件「测试账号在哪」。不要把密码抄进 Git。

## 用户说「同步」

同一账号日常说「同步」：把尚未回写仓库的共用改动开 PR，总控不自己合并。

换到新 Grok Bot 账号或新机器后，或要把一个账号的工作台同步到另一个账号时，固定顺序和恢复验收只以 `grokbot/BACKUP.md` 的「用户说「同步」」和「恢复与同步检查清单」为准。接收的一方是当前账号，提供备份或映射的一方是来源账号。方向不写死。本文件不另抄一套。测号位置仍见本文件「测试账号在哪」。连接器要重新授权。云电脑日常开工仍跑 `/workspace/qa/qa-ready.sh`。

接手时按该检查清单做，不要漏掉这几条：

- 不止拉 Git。还要读来源账号目录的最新完整备份，并查比它新的增量包或 skill-sync 包。从中读规则、技能、角色说明、协作规范、工作台映射。记录源文件、更新时间、账号。
- 核`工作台-<当前账号>`和`派单记录-<当前账号>`。需要对照时再看`工作台-<来源账号>`和`派单记录-<来源账号>`。三种入口都核：角色主对话、需求或主题子对话、Project 协调器。
- 当前账号逐个核对自己现有机器人应有的工作台：映射是否对、能否打开、能否续聊。能复用就复用并补登。窗口在、映射缺，就补映射。确实未建、且现有规则要求有工作台，才按规则建正确类型，登记并读回。无权限或找不到不是可以重建。
- 当前账号页是空的、仓库旧快照、旧机器人停用标签、当前账号 Projects 列表没有记录，都不能单独当成所有入口缺失。机器人停用不等于已有的 Cursor 对话失效。
- 备份包不覆盖仓库技能和现网技能。记忆不对倒。不把来源账号的机器人 id 或技能 id 抄过来当成当前号。凭证、密钥、测号明文不进 Git，也不打进备份包。
- Git 拉完不算同步完成。只找到来源账号的映射也不算。验收要有每个当前机器人的核验、已补项、读回和未解决阻塞。

## Cursor 两条通道

工作台给思考、方案、代码草稿。默认模型是 Grok 4.7。常驻是每个在用项目号一条对话。需求分析是一条需求一条对话。同类活续聊。不提前建满。

升级走常驻 Ask、Plan、Debug、Multitask，再加上 `tools/ask_cursor.py`。一事一案，一个 Agent，一个 PR。工作台不替代升级。

本文件原有说法：映射正本在 `grokbot/workbench-map.md`，谷歌表「QA机器人Cursor工作台」只是同步副本。`grokbot/BACKUP.md` 和常驻规则包另有「正本在表」的说法。两套并存，恢复时不自动改认，见该文件「正本冲突先挂起」。页按账号分开，页名是`工作台-<账号名>`和`派单记录-<账号名>`。查、写进当前账号自己的页。来源账号的页只作对照，不把来源账号的稳定 id 或对话当成当前号。停用或空行也不等于那些 Cursor 对话失效。下面是仓库快照里已经记下的例子，不是同步方向：工作台-Faker 里，总控（King）常驻、自动化踩坑知识库常驻已是「在用」。T8T需求分析「故事220」和「故事221」需求分析行已是「在用」，未写入该号常驻行。其余该页行的对话 URL 和对话 id 仍为空，状态仍为「空」。不要给那些行编造对话。三种入口、补齐和恢复验收见 `grokbot/BACKUP.md` 检查清单，本段不另写。
